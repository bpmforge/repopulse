Notes on individual rows:

- **Swift Package Manager** (Supported: read and matched): Matched since W18-51. Before it, grype matched nothing although the database holds three active swift-nio advisories whose ranges include 2.40.0: syft catalogues the package as `swift-nio` and keeps the repository path only in the purl (`pkg:swift/github.com/apple/swift-nio@2.40.0`), while grype looks a package up by the name it is given and the database indexes it as `github.com/apple/swift-nio`. Measured on the real tools: the same package matched nothing as catalogued and three advisories once its name was the purl path. The scanner now gives grype a copy of the SBOM in which a namespaced Swift package is named by its purl path (`deploy/scan-tools/sbom-normalise.mjs`); the SBOM it returns is syft's own.
- **CocoaPods** (Read, not matched): The database DOES hold an advisory for this exact version (CVE-2015-3996, AFNetworking <= 2.5.2), so this is not missing data. It is an NVD record keyed by the CPE vendor `afnetworking_project`; syft generates the vendor `AFNetworking`; grype joins on vendor and product, so nothing matches. A CPE with the real vendor, or with a wildcard vendor, does match it (measured). The wildcard is not safe: it matches on the product name alone. On the 103,421-pod CocoaPods index, 1,152 NVD products share a pod's name and 771 of those exist only under unrelated vendors (the `nimble` pod would collect Apache NimBLE's 15 advisories, `toast` Roxio Toast's, `sentry` 33 from other vendors, `stripe` and `paypal` WordPress and e-commerce plugin advisories). The NVD's `<name>_project` vendor pattern covers 217 of them but includes plain words (`async`, `cache`, `console`, `date`, `diff`) that are other ecosystems' projects. So no join is applied and the row stays unmatched. A sound join exists: accept an NVD candidate only if one of its CVEs references the pod's own source repository, taken from its podspec (which a Podfile.lock does not carry). Measured in W18-54 on a seeded 200-pod sample: it verified 5 pods (2.5%, about 29 of the 1,152 candidates, every one correct, including vendors no name rule could guess), while a wildcard vendor was 98% wrong and a name or name_project vendor rule 94% wrong. It needs the CocoaPods Specs as a new data source and a maintained table for roughly 29 pods, so it is not built: the owner chose to leave CocoaPods unmatched for now (W18-54, option A, 2026-10-25), and to revisit with a reviewed alias table if iOS customers appear.
- **vcpkg** (Unsupported: not read): syft has a vcpkg-manifest-cataloger, but it reads the manifest's OWN name and version only (measured: one package, the project itself), never its dependencies, with or without an exact `overrides` pin. A vcpkg manifest's dependencies carry no resolved version unless overridden (vcpkg resolves them from its registry baseline at install time), so there is nothing to match offline apart from `overrides`. A reader for those would also have to guess each C/C++ library's NVD vendor, the same join problem as CocoaPods. Investigated in W18-52 and not built.

How to read a row:

- **Supported** means syft read the pinned package from the lockfile *and* grype reported a vulnerability for it. Both halves matter: a lockfile that is read but never matched finds nothing.
- **Read, not matched** means syft read it and grype matched nothing. That is never proof the package is safe: the cause is stated under the table for each such row (the database holds no advisory for that version, or it does and no key joins it to the package). A row here is not safe to rely on until a known-vulnerable package matches.
- **Unsupported** means syft reported no such package from the fixture. Dependencies in that ecosystem are invisible to the scanner, and the coverage map should say so.
- A repository can still hold a lockfile the fixture does not exercise (a newer lockfile version, a monorepo layout). The fixture proves the format is read, not every variant of it.
