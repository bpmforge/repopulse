# RepoPulse — end-user walk, 2026-08-27

A second review, done as a user rather than as a reader. Two installs:

- **Install A — real (non-demo).** `pnpm dev`, no `DEMO_MODE`, no GitHub App,
  no forge credential. Bootstrap admin, forced password change, zero
  repositories. This is what a self-hosted customer actually starts with, and
  it had never been exercised before today.
- **Install B — demo.** `DEMO_MODE=1`, seeded warehouse, admin role, every
  drill-down populated.

Findings are labelled by install. The rule from the first review still holds:
**nothing is filed as a defect on a screenshot alone** — each item below cites a
server log line, a source read, or a repeated interaction. Anything resting on
appearance only is marked *observational*.

## A1 — A signed-in user whose account is deleted is stranded, permanently

**Severity: highest thing found in either review.**

I hit this twice by accident, which is the point: it is not exotic.

With a valid session cookie whose user row no longer exists, the shell shows
**"Checking your session…" forever**. No error, no retry, no sign-out, no way
back. The tab is bricked; only clearing cookies recovers it, which is not
something you can tell a user over the phone.

Server side (`user1.log`):

```
"url":"/api/v1/me/context" → "msg":"unhandled error" → "statusCode":500
PostgresError: insert or update on table "workspace_members"
  violates foreign key constraint "workspace_members_user_id_users_id_fk"
```

`ensureMembership` inserts a membership row for a user that is gone.

What makes this worse than a 500: the shell was *designed* for exactly this.
`__root.tsx:135` has an `unknown` branch, commented "the probe itself failed
with something that is NOT a 401 … that is not evidence anyone is signed out,
so the app renders and each widget reports its own error honestly". **That
branch is never reached.** The probe stays on `loading` indefinitely, and only
ONE request is made — no retry, despite `queryClient.ts:15` retrying non-4xx
twice. So the query neither succeeds, errors, nor retries.

I could not confirm the client-side mechanism in the time available; the
server-side cause and the user-visible result are both confirmed. The fix
belongs in the session preHandler — reject the session and clear the cookie
before anything tries to write on behalf of a user that no longer exists —
rather than in `ensureMembership`.

Reachable in any install where an admin removes a user who is signed in
elsewhere. Filed already as **W16-15**; this raises it from "500 instead of
401" to "unrecoverable dead end", which is a different priority.

## A3 — Three of the four in-app help links lead to A2

`definitionHref` points at `/docs/INSTALL.md` (Connections) and
`/docs/design/METRICS.md` (File detail, Settings). The app does not serve
`/docs`, so all three resolve to the not-found placeholder above.

The Connections one is the worst placed of the three: it is the ⓘ on
**Connect an organisation**, which is the screen a new admin is sent to by the
welcome state, at the exact moment they need to know what credential to create.

## A4 — The setup checklist's doc references are not links, and not reachable

`/setup` is the best screen in the product — the checklist is specific and
honest about what is unknown versus what is wrong. But each item ends with a
bare `<span>See {check.docs}</span>` (`routes/setup/index.tsx:96`), rendering
`See docs/INSTALL.md#connect-your-forge` as text.

On a **container** install — the shipping shape — the customer has no repository
checkout, so `docs/INSTALL.md` does not exist on their machine in any form.
Five references, none reachable.

## A5 — GitHub is the one forge whose token field does not say what it needs

`Connections.tsx:146`:

| Forge | Label |
|---|---|
| GitLab | "GitLab personal access token (**read_api**)" |
| Gitea | "Gitea access token (**read:repository**)" |
| GitHub | "GitHub token or installation credential" |

GitHub is the primary, README-first forge and the only one that does not name a
scope. A user creating a PAT has to guess among `repo`, `public_repo`,
`read:org`; the wrong guess fails later, during ingestion, far from the form.
The placeholder — `ghp_… or an app installation id` — offers two different
kinds of credential without saying when to use which.

## A6 — The persona picker interrupts the first thing the product asks you to do
*(observational)*

The welcome state says "Connect your organization to start ingesting history"
and now offers a button. Clicking it raises a modal first: **"What best
describes you? This picks your home screen."**

At that moment there are no repositories, no PRs and no findings, so every
option describes a screen that will be empty — "My PRs, my review queue, code I
own" for an account that has none. It is also mandatory: there is no "decide
later". A first run should let someone complete the action they were just sent
to do.

# Install B — demo, with data

The goal, rather than a tour: **"Which repository most needs attention this
week, why, and what do I do about it?"** — following only what the UI offers.

I could answer *which* and *why*. I could not get to *what do I do*, and two of
the numbers along the way contradict each other.

## B1 — "Run scans now" cannot run anything, on any repository

**Severity: a feature that does not work at all. Mine, shipped in W16-10 today.**

Repo → Security lists six scanners; four say "enabled, has never run". Pressing
**Run scans now** answers:

> Nothing to run (request req-1q)

The button and the table disagree on screen, in the same card, one above the
other.

The table is right and my route is wrong. `isEnabled(key, stored)`
(`packages/security/src/config/defaults.ts:60`) falls back to
`defaultFor(key).enabled` when there is **no** `repo_scanner_config` row — so a
scanner enabled by default reads "enabled" with nothing stored. My route
(`routes/runs/index.ts`) selects rows from `repo_scanner_config` and finds none.

So Run-now works only for a repository whose scanner config someone has
explicitly toggled at least once — which is no repository on a fresh install.
The fix is to resolve through `listScanners()` + `isEnabled()`, the same source
the coverage table uses, instead of reading rows.

Bright spot: the refusal carried `(request req-1q)`, so W16-18's request id is
working on a real write surface.

## B2 — The score screen says "Review 0" directly above a chart reading 40%

Repo → *why?* on acme/infra decomposes the score honestly and the arithmetic
checks out (17.2 + 0 + 9.3 + 11.0 = 37.5 ≈ 38):

```
Activity  86 x 0.2  = 17.2
Review     0 x 0.3  =  0.0     ← the whole 30% weight, lost
CI        37 x 0.25 =  9.3
Delivery  44 x 0.25 = 11.0
```

Scroll down on the *same tab* and "Review coverage" reads 20–50%, ending at 40%.

Both are correct and the screen makes them look contradictory. `reviewHygiene`
normalises `m5` with `good: 0.9, bad: 0.4`
(`packages/insights/src/score/health.ts:193`), so 40% coverage sits exactly on
the **bad** anchor and normalises to 0. "Review 0" means "0 on our normalised
scale", not "no reviews happened" — and a reader has no way to know that.

The product already solves this elsewhere: the generated report's breakdown has
**Raw | Normalized | Weight | Contribution**, showing `reviewHygiene · m5 · 0.4
· 0`. The repo screen (`HealthWhy.tsx:92`) prints only `{normalized} x {weight}
= {contribution}`. The screen people actually look at is the impoverished one.

## B3 — The report's Contribution column does not sum to the score

From the report generated in this pass (`/print/reports/1177`):

| Sub-score | Input | Raw | Normalized | Weight | Contribution |
|---|---|---|---|---|---|
| activity | daysSinceLastPush | 5.87 | 86.18 | 0.2 | 17.24 |
| reviewHygiene | m5 | 0.4 | 0 | 0.3 | 0 |
| reviewHygiene | stalePrCount | 175 | 0 | 0.3 | 0 |
| ciHealth | m9PassRate | 0.86 | 74.29 | 0.25 | **9.29** |
| ciHealth | topFlakiness | 0.5 | **0** | 0.25 | **9.29** |
| delivery | e2eCycleP50Hours | 145 | 43.98 | 0.25 | 11 |

An input normalised to **0** cannot contribute **9.29**. The column is the
SUB-SCORE's contribution repeated on each of its input rows, not the input's.

Summing it gives 46.8 against a stated score of 38. This is the exportable
deliverable, and its whole design invites the reader to check the arithmetic —
"Raw severity is shown beside every score", "regenerating this report
reproduces these numbers exactly". Anyone who adds the column up finds it wrong.

(The per-sub-score numbers are right: 17.24 + 0 + 9.29 + 11.0 = 37.5 ≈ 38.)

## B4 — "Needs attention" does not rank, and its order is not stable

`/org/attention` (`routes/org/index.ts:105-116`) selects repositories with **no
`ORDER BY`**, loops them, and pushes any in band C/D/E. The card renders that
order.

On the overview it shows payments (Medium), web-app (Low), infra (Medium) —
not sorted by severity, and infra (score 38) is last despite being the worst
repository in the workspace. With three repositories it is untidy; with two
hundred it is a triage card you cannot triage from, and because there is no
`ORDER BY` the order may differ between refreshes.

## B5 — A finished report never stops saying "running"

Confirms **W16-12**, which I had filed as unverified.

Pressed Generate once. The row appeared immediately as "running" — good, and it
re-confirms that F9 was correctly retracted. The server finished the job:

```
"event":"report.generated" ... "reportId":1177  20:50:35
```

The row still read "◐ running" ~50 seconds later. Over that time the client made
**2** `GET /api/v1/reports` — the initial load and the post-mutation refetch —
against a `refetchInterval: 3000` that should have produced roughly sixteen.

Caveat: I cannot rule out that an extension-driven tab counts as unfocused,
which is exactly the `refetchIntervalInBackground` case W16-12 names. Either way
the user-visible outcome is now demonstrated rather than hypothetical: a report
that is ready is displayed as running, and only a manual reload corrects it.

## B6 — The demo warehouse reports 175 stale PRs across 15 PRs
*(observational; affects the demo, not the product)*

The report's PR Flow table gives **M8 Stale PRs = 175** for a workspace the
seeder describes as 15 PRs total. That number is what drags `reviewHygiene` to 0
(the input's "bad" anchor is 10), so the demo's headline health scores are
shaped by a figure that cannot be right. Worth fixing because the demo is the
first thing anyone judges the product by.

# What is genuinely good, from a user's seat

- **`/setup` is the best screen in the product.** The checklist separates "not
  configured" from "configured and unverified" — "No webhook delivery has
  arrived yet. That is expected before your first push — it is not proof the
  webhook is wrong, and not proof it is right."
- **The *why?* breakdown shows its arithmetic** and it adds up. Almost nothing
  in this category will show you the formula.
- **The uncertainty copy remains the differentiator**: "4 not measured … which
  is neither a grade nor a zero", "It is not zero — it is unmeasured", "not a
  ranking of people".
- **Fixes from earlier today are live and correct**: report Markdown renders,
  the print view has a way back, the Basis table names repositories, breadcrumbs
  read "Org › Repos › Security", and a failed write carries its request id.
