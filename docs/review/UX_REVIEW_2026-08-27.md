# RepoPulse — end-user UX/UI review (2026-08-27)

Method: dev stack (`DEMO_MODE=1 pnpm dev`, localhost:5273) driven in Chrome,
plus a real `podman compose -f deploy/compose.yaml up -d --build` of the
customer-hostable stack. Code read only to explain what the UI does.

**Not covered — and one of these matters more than anything below.**
- **The non-demo first-run flow was never exercised**: real local sign-in,
  the forced password change on first boot, `/setup`, Admin → Connections
  against a real forge. For a product pitched as standalone and self-hosted
  that is *the* critical path, and it is the highest-value next pass. Demo mode
  mocks exactly that boundary, so nothing here says whether it works.
- **Responsive layout**: partially seen and it looks bad (see F21), but not
  systematically tested.
- No axe/Lighthouse run; accessibility notes below are observational only.

**Standing rule adopted mid-review, after three retractions.** F12, F17 and F9
were all filed on the strength of what a browser screenshot appeared to show,
and all three dissolved under a second check — a mis-click after a late window
resize, an accessibility read before hydration, and a query poll that pauses in
an unfocused tab. Browser observation in this setup is not a reliable oracle.
Every finding that survives is backed by a source read, a server log line, or a
Playwright run; anything resting on a screenshot alone is marked observational
and ranked P2. That distinction is worth more than any single finding here.

## P0 — the documented first-run path does not work

**F1. Demo mode's headline promise is false for the form it puts first.**
README.md and docs/RUNNING.md both say "any login lands you as the fixture
user", and the API prints the same sentence on boot. It is only true of the
*GitHub* button. Typing anything into the Email/Password form — which is the
primary, auto-focused control — returns "Invalid email or password"
(`auth.login.failure / invalid_local_credentials`, dev.log:52).
Demo mode mocks the OAuth boundary (apps/api/src/demo.ts:81-85), not the local
credential path. A first-time user follows the quickstart verbatim and is
locked out on screen one.
Fix options: (a) in demo mode, seed the fixture user as a real local account
and print those credentials, or (b) hide the local form in demo mode and leave
only the mocked button, or (c) correct both docs to say "click Sign in with
GitHub".

**F2. (P2, observational.) The sign-in screen has no demo banner.** The banner ("Demo mode — fake
forge, mocked sign-in, seeded fixture data") appears only *after* login. The
one screen where a user needs to be told "type anything / click the button" is
the one screen that says nothing. It also still says "Accounts are created by
your RepoPulse administrator" — in a standalone self-hosted product the user
*is* the administrator, so this reads as a dead end.

**F3. `Sign in with GitHub` renders even when no OAuth app is configured.**
docs/RUNNING.md claims the API "simply offers no GitHub button" without
`GITHUB_APP_CLIENT_ID`. In demo mode it is present (correctly, it is mocked) —
needs re-verification in the non-demo dev stack, where the same button pointing
at an unregistered OAuth app would fail off-site.

## P0 — the container stack does not come up

**F4. `podman compose -f deploy/compose.yaml up -d --build` starts 5 of 6
services; the ingestion worker never starts.**
`Error: statfs /var/lib/repopulse/scan-rules: no such file or directory`, then
`exit status 125`. Cause: `SCAN_RULES_DIR` defaults to an absolute host path
(compose.yaml:132) that does not exist on a clean host and that nothing in the
up-path creates — it is filled by `deploy/scan-db-sync.sh`, run manually, and
needs ~2 GB (grype DB). This is a *known* failure — docs/RUNBOOK.md:165 names
the exact error — but it is still the default out-of-box result.
The damage is that the web UI comes up healthy on :8099 and answers 200, so the
user sees a working product that will never ingest anything, with the only
evidence buried in a compose log line they already scrolled past.
Fix: make the scan mount optional (worker degrades to "dependency scanning
unavailable" instead of refusing to boot), or have compose/bootstrap create and
populate the directory, or fail the whole `up` loudly rather than leaving a
healthy-looking web tier.
This matches the board: W11-01 and W11-05 are both still `blocked`.

**F12. (RETRACTED — not a defect. The links work.)** Reported as "repo
drill-down links dead by mouse and keyboard", ranked the most severe pure bug.
It is a testing artifact, and the retraction matters more than the finding did.

What actually happened: the original click used coordinates from a screenshot
taken before a window resize had applied, so it landed in the wrong place. The
"confirmation" then used `left_click` by accessibility ref and a keyboard
Enter — and in this browser-extension build a ref-click does not activate a
link, which made a passing app look like a broken one twice in a row.

Disproved three ways: a coordinate click on a repo row navigates to
`/repos/25243`; the same is true of the rail links and the sign-in button; and
a Playwright test added for this ticket (`e2e/repo-detail.spec.ts`, "the
/repos list rows navigate, by click and by keyboard") passes against the
seeded stack, by click AND by Enter.

The test was kept. It covers a real gap — the `/repos` list had no
click-through coverage of its own, only the org-overview tile did — so the
ticket produced a regression guard even though the bug was imaginary.

Lesson worth keeping: in-browser observation needs a second, independent
confirmation before a P0 is filed. Everything else in this document was
verified against the API log, the compose output, or the source.

## P0 — "bring your own LLM" is not a thing the product supports

You described RepoPulse as standalone, with users connecting their own LLM —
cloud, local, whatever. As built, that is not possible. Three separate walls:

**F5. There is no UI anywhere to configure an LLM.** Admin → Analysis
(screenshot) is a per-repo two-checkbox table — "Tier 2 (local)" and
"Tier 3 (Claude API)" — plus an egress audit log. No endpoint field, no model
field, no API-key field, no connection test. Admin → Setup is explicitly
read-only ("Whether each variable is set — never its value"). Every LLM
setting is an env var (`LMSTUDIO_BASE_URLS`, `LMSTUDIO_MODEL`,
`ANTHROPIC_API_KEY`), so changing model or provider means editing a file on the
host and restarting the container. For a self-hosted product whose whole point
is that you plug in your own model, that is the single biggest gap.

**F6. The provider names are hardcoded into the product's vocabulary.** The UI
says "Tier 2 (local)" / "Tier 3 (Claude API)", "sends the diff … to Anthropic",
"Rejected LM Studio host …". Env vars are `LMSTUDIO_*`. The *good* news, and
this is the actionable part: `packages/analysis/src/t2/client.ts` already
speaks plain OpenAI-compatible `POST /v1/chat/completions` and normalises the
base URL. So the wire format ALREADY works with Ollama, vLLM, llama.cpp,
LM Studio, OpenRouter, Groq, Together, and OpenAI itself. The generalisation
is mostly renaming plus two real code changes (F7).

**F7. Tier 2 is hard-blocked from ever reaching a cloud endpoint — by design,
in two places.**
  1. `packages/analysis/src/config/hosts.ts` rejects any non-RFC1918 host
     unless `allowPublicHosts` is set, and rejects *hostnames* outright even
     with it (comment: "A name that resolves privately today is not a guarantee
     about tomorrow"). `api.openai.com` cannot be a Tier-2 host.
  2. `T2_REQUEST_HEADERS` is a frozen `{content-type}` — no Authorization
     header is possible — and `containsCredentialMaterial()` actively treats a
     bearer token in the payload as a violation. Every hosted provider requires
     a key.
So the only "bring your own" path is a LAN box running LM Studio, and the only
cloud path is Anthropic specifically, gated behind per-repo opt-in.
This is a deliberate security posture (SC-24, NFR-9), not an oversight — it is
just incompatible with the product you described. Reconciling them is a product
decision, not a bug fix. Suggested shape: keep the strict default, and add an
explicit "custom provider" connection (base URL + optional API key stored
encrypted like forge tokens, model id, a Test connection button) that carries
the same egress-audit treatment Tier 3 gets — so a user pointing at OpenAI
gets the audit row rather than the refusal.

**F8. A misconfigured LLM is invisible in the UI.** The worker logged
`analysis gateway: NOT CONFIGURED (LMSTUDIO_BASE_URLS is set but LMSTUDIO_MODEL
is not) — scheduled judgement passes will skip and say so`. That is an
excellent message, and it appears only in a terminal. Admin → Analysis, the one
screen about analysis, shows nothing: the Tier-2 checkboxes look ready to arm.
The gateway's configured/not-configured state and its reason belong on that
page.

## P1 — bugs on the happy path

**F9. (RETRACTED — could not be reproduced.)** Reported as "Generate appears
inert; the history never refetches, so you press it twice". Re-tested against a
live demo stack: one click produced one row within 6 seconds, and the server log
shows exactly one POST. The invalidation is correctly wired
(`useApiQuery.ts:154-169`) and the original double-report was a mis-click, same
root cause as F12.

One question is left genuinely open rather than closed: the history sets
`refetchInterval: 3000` so a `queued`/`running` row can flip to `ready` on its
own, and TanStack pauses that interval when the document is unfocused
(`refetchIntervalInBackground` defaults to false). A browser-extension-driven
tab is not a reliable way to test that. Whether a report finishing in a
backgrounded tab ever updates is UNVERIFIED — it needs a Playwright test with
explicit focus control, not another screenshot.

**F10. Generated reports leak raw Markdown into the rendered page and the PDF.**
`/print/reports/1122` renders literal `**3 open findings**`, `**acme/infra**`,
`` `act` `` — asterisks and backticks shown as text. The report body is Markdown
being dropped into the DOM unrendered. This is the product's exportable
deliverable, the thing a user shows their VP, and it looks broken.

**F11. Repository IDs are shown to users instead of names, inconsistently.**
Admin → Sync lists repos as `25154 / 25153 / 25152`. The report's "Basis" table
does the same — then the very next paragraph of that same report says
"**acme/infra** scored 38 (D)". Numeric ids are internal; they should never
surface.

**F13. (P2, observational — not re-verified.) The print/report view is a trap.** `/print/reports/:id` replaces the app
shell entirely — no nav, no breadcrumb, no Close. The only exit is browser Back.

**F14. (P2, observational.) Finding detail opens partly below the fold, with no scroll-into-view.**
On /findings, clicking a finding renders the detail panel underneath the table.
At 1440x900 the panel header and evidence are visible but the actions
(Note / Dismiss reason / Confirm / Dismiss) are not — you must scroll to find
out that clicking did anything useful. Also the URL never changes, so a finding
cannot be linked to or shared — for a triage tool whose workflow is "look at
this one", that matters.

## P1 — nothing can be triggered from the UI

**F15. There is no "run it now" anywhere.** Every scan and sync is cron-driven
(`RECONCILE_CRON`, `SECURITY_WEEKLY_CRON`, …). Repo → Security and Repo → Code
Health both show tables of scanners that have "never run", with no button to
run one. Admin → Sync reports progress but offers no Sync now. For a product a
user just installed on their own machine and wants to see work, "wait until
Sunday 02:41" is the wrong answer.

**F16. Every scanner reads `(not installed)` with no path to installing it.**
Repo → Security lists six scanners, all `(not installed)`. The UI names the
problem and stops. A local-container product should either ship them in the
worker image or link to the one command that provides them.

## P2 — polish, accessibility, copy

**F17. (retracted after verification — not a defect.)** An early
accessibility-tree read showed the sidebar and repo links with empty accessible
names. Re-reading after full hydration returned `link "payments"` correctly, and
`Rail.tsx:153` renders the label as a real text child. This was a
read-before-hydration artifact, not a WCAG failure. One narrow case remains
worth a look: with the rail collapsed the label span is not rendered and the
name falls back to `title=`, which is a weak source. A full axe pass is still
worth running, but nothing here is confirmed broken.

**F18. Chart axes carry no units.** Repo → Pulse plots "PR cycle time" up to 180
and "Review coverage" 50→10 with bare numbers. The KPI tiles get this right
(`159 h`, `153 lines`, `50 %`); the charts do not.

**F19. Breadcrumbs never name the current page.** On `/repos/25152` the
breadcrumb reads "Org › Repos" — the repo you are looking at is missing from
its own trail. Same on the Admin sub-tabs.

**F20. The repo list's badge has no legend.** `/repos` shows `payments 39`,
`web-app 61`, `infra 38` in coloured pills with no column header and no
tooltip. It is the health score, but the list never says so — and the same
number on the repo page is accompanied by a "why?" link and a "4 not measured"
caveat that the list drops entirely.

**F21. The layout does not adapt to a narrow window.** At ~420px wide the rail
stays at its full 240px and never auto-collapses, the content column is pushed
off-screen, the page scrolls horizontally, and repo names truncate to "pay…" /
"we…". The rail already has a working collapse toggle and a `w-16` collapsed
state (`Rail.tsx`) — it simply is not driven by a breakpoint. Seen
opportunistically rather than tested properly; a real responsive pass is
outstanding.

## What is genuinely good — do not regress it

- **The empty-state and uncertainty copy is the best thing in the product.**
  "No dependency scan has run … so this is not a clean bill of health."
  "It is not zero — it is unmeasured." "No complexity findings. If the coverage
  table says the scanner has never run, that is why — this is not a measurement
  of a tidy codebase." "an empty log means no call was made — not that one went
  unrecorded." Almost nothing ships with this discipline about the difference
  between zero and unknown. It is a real differentiator; keep it.
- The demo banner (post-login) is unmissable and states exactly what is fake.
- Findings carry a Verification column — "verified by a second model",
  "contradicted on review" — which is the right answer to LLM false positives
  and is not something competitors surface.
- "View as table" on every chart, `sr-only` captions, a required note before any
  status change, "4 not measured" beside the score, the health-score breakdown
  table in the report showing raw → normalized → weight → contribution.
- Admin → Analysis's egress framing (written before the call, not after).

## Recommended order

1. F1/F2 — demo login. One evening. Nothing else matters if screen one rejects you.
2. F4 — worker won't start in the container. Make the scan mount optional.
3. F9/F10 — Generate feedback and Markdown rendering. Both small, both on the
   path to the product's exportable deliverable.
4. F5-F8 — the bring-your-own-LLM decision. Needs your call before any code
   (see below), then a Connections-style provider form.
5. F15/F16 — a Run now button and a scanner install story.
6. F11, F13, F14, F18-F21 — polish sweep.

## The one decision only you can make

The product you described ("users connect their own LLM, cloud or local or
whatever") and the product that is built (LAN-only credential-free Tier 2,
Anthropic-only Tier 3, both configured by env var) are different products. The
current design is a deliberate, well-argued security posture — SC-24's comment
about the metadata endpoint is correct and the credential-free header set is a
real control. Loosening it to accept an arbitrary base URL plus an API key is a
threat-model change, not a feature toggle, and it should be decided explicitly
rather than drifted into.
