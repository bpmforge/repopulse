### Step 11 in detail — the model-timeout drill

Providers replaced with `fixture-hang`. Its own Test connection reported,
inside the run: `Could not connect. The operation was aborted due to timeout`.
The scan then ended on the CLIENT's deadline (`LMSTUDIO_REQUEST_TIMEOUT_MS=30000`
set by the overlay), not a test timeout:

```
state: error, last_run_status: failed
error: "the model did not finish within 30s — it may be loaded on a busy host, or the prompt may be too large for it"
```

`model-requests.txt` shows the fixture side: `model=fixture-hang … -> HANGING
(waiting for the client to give up)` followed by `client gave up and closed the
connection` — the product does hang up, it does not leak the request.

Recovery: provider swapped back to `fixture-model`, scan re-run:

```
state: all_rejected, last_run_status: succeeded, error: null
validation_funnel: { chunks: 1, created: 0, proposed: 1, rejected: 0 }, open_findings: 1
```

**Honest residual (not a failed recovery).** The model answered and the run
succeeded with no error; that is what the drill proves. The row reads
`all_rejected` rather than `ok` because step 8 had already created this repo's
single fixture finding, so the re-run's one proposal was deduplicated against
the open finding — created 0, rejected 0. The state label conflates "nothing
new was created" with "everything was rejected"; a scanner status that names
the deduplicated case is a small follow-up for the security widget, recorded
here rather than papered over. The spec's recovery assertion therefore
requires a succeeded, error-free run with a non-error terminal state, and
checks the screen's `data-state` matches the API's.

Screenshot 19 captures the security page after recovery at the top of the
table; the OWASP row is below the fold in that viewport. The row's state was
asserted from the DOM, not the image.

## What this ticket changed (found by the journey, not declared)

- `apps/api/src/routes/runs/index.ts` — "already running" now means RUNNING.
  A completed or failed job that still held its BullMQ id inside the dedupe
  window answered "already running" for five minutes after the CVE scan failed
  for want of a database and the operator fixed it and pressed again.
- `apps/api/src/workers/gateway.ts` — a cached ABSENT gateway (no provider) is
  reused for 5 s, not the full 60 s; adding a model in Admin → Models and
  scanning immediately no longer reads "No model is configured" for a minute.
- `deploy/demo.sh` — `DEMO_COMPOSE_OVERLAY` / `DEMO_EXTRA_SERVICES`, so the
  journey layers one service on the demo stack rather than being a third stack.
- New: `deploy/journey.sh`, `deploy/compose.journey.yaml`, `deploy/journey/`
  (fixture model), `e2e/journey/` (spec + harness),
  `playwright.journey.config.ts`; `playwright.config.ts` ignores `journey/**`.
- Gap recorded in the spec, not worked around silently: no screen enables a
  per-repo scanner; step 8 enables `owasp_web` through `PUT /scanners/:key`.
