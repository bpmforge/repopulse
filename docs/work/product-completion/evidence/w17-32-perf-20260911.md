## 2. Bounds at 100 repositories / 10,000 findings — what was NOT bounded

Two things grew with the data on tip code. Both are in `apps/api/src/routes`
(this ticket's write scope) and both are fixed in this working tree.

### 2a. SQL statements per request (one request, exact count)

| Endpoint | 3 repos, before | 100 repos, before | 100 repos, after | 3 repos, after |
|---|---|---|---|---|
| `/api/v1/repos?window=30d` | 26 | **706** | **8** | 8 |
| `/api/v1/org/health-tiles?window=30d` | 26 | **706** | **8** | 8 |
| `/api/v1/org/attention?window=30d` | 26 | **706** | **8** | 8 |
| `/api/v1/org/summary?window=30d` | 9 | 10 | 10 | 10 |
| `/api/v1/findings` | 5 | 6 | 6 | 6 |
| `/api/v1/findings?sort=severity` | 5 | 6 | 6 | 6 |
| `/api/v1/findings?status=open&dimension=security` | 5 | 6 | 6 | 6 |
| `/api/v1/findings/stats` | 6 | 7 | 7 | 7 |

Cause: `routes/org/health.ts` `repoHealth` read six metric snapshots plus the
workspace settings per repository, and the three list routes called it once
per row — 7 statements × 100 repos + 6. Fix: `repoHealthMany` reads every
(repo, metric) latest snapshot in one `DISTINCT ON` query and the settings
once; `repoHealth` is now that function with a list of one, so the scoring
cannot drift between the detail and the lists. The count is 8 at 3 repos and 8
at 100 (the session/CSRF/workspace lookups the request pipeline does, plus the
repo list, the snapshot read and the settings read).

The +1 on the other endpoints between 3 and 100 repos (5→6, 6→7, 9→10) is
present in the before AND after columns and did not change with this ticket;
it is not a per-row growth.

### 2b. Payload bytes (one request)

| Endpoint | 3 repos | 100 repos / 10k findings | Items |
|---|---|---|---|
| `/api/v1/repos` | 928 B | 31,095 B | 3 → 100 (one row per repo, no page) |
| `/api/v1/org/health-tiles` | 310 B | 10,398 B | 3 → 100 |
| `/api/v1/org/attention` | 290 B | 9,107 B | 3 → 98 |
| `/api/v1/findings` (any filter/sort) | 2,428 B | 54,507 B | 3 → **50 (PAGE_SIZE)** |
| `/api/v1/findings/stats` | 224 B | 1,171 B | aggregate |
| `/api/v1/org/summary` | 358 B | 358 B | 5 tiles |

Findings payloads are bounded by the page size (50 rows, ~54 KB) regardless of
the 10,000 in the table. Repo-level lists are bounded by the repository count
(≈311 B per repo on `/repos`), which is the product's unit of scale; they are
not paged and this ticket did not add paging (that would be a redesign).

### 2c. Findings keyset paging — FACT: was returning 6% of the rows

Full walk of `/api/v1/findings` following `next_cursor` to the end, at 10,000
rows:

| Sort | Before: pages / distinct ids / duplicates / missing | After |
|---|---|---|
| `risk` (the default) | 23 / **610** / **270** / **9,390** | 200 / 10,000 / 0 / 0 (1,689 ms) |
| `severity` | 200 / 10,000 / 0 / 0 | 200 / 10,000 / 0 / 0 (1,529 ms) |

Cause: the cursor encoded `(severity, id)` under both sorts while the default
sort ordered by `effective_risk DESC NULLS LAST, severity, id`, so the "after
this row" predicate and the ORDER BY disagreed. Fix in
`routes/findings/index.ts`: the cursor now carries the sort key it was minted
under (`r:<effective_risk|->:<severity>:<id>` for risk, unchanged for
severity), the predicate matches the ordering including the NULLS LAST block,
and a cursor from the other sort is refused with 400 rather than misapplied.
`routes/findings/paging.test.ts` inserts 130 findings with tied risks and
NULLs and walks both sorts; run against the tip code it fails (131 rows for
130 findings, cross-sort cursor accepted), against the working tree it passes.
This was invisible at the seeded size (3 findings = one page).

## 4. Residuals, stated

- **Sub-10 ms API timings at 3 repos are 2–3 ms slower in both after runs**
  (`/findings` p50 4.3 → 6.7 → 6.7 ms; `summary` 4.0 → 7.2 → 6.9;
  `stats` 4.1 → 7.3 → 7.4). The shift is uniform across endpoints this ticket
  touched and endpoints it did not (`summary`, `stats` are unchanged code),
  and it is absent at 100 repos on the same endpoints (`/findings` 10.9 →
  11.4, `summary` 7.2 → 5.4), so it is attributed to the state of the
  restarted API process/host rather than to the change. Dead tuples from the
  fixture teardown were ruled out (`pg_stat_user_tables`: 0 dead on
  `findings` and `metric_snapshots`, autovacuumed before run 2). It is not
  explained beyond that, so it is reported here rather than absorbed. The
  acceptance's 20 % rule is applied to the repeated page loads in §3, none of
  which regressed in either after run.
- **Repo-level lists are not paged.** At 100 repos `/repos` is 31 KB and 100
  rows; at 1,000 it would be ~310 KB. Bounded by repository count, not by a
  page size. Not changed here (redesign).
- **Dev-server timings.** Browser numbers are against Vite dev, not the
  built bundle; §1 is the only production-bundle measurement.
- **`attention` at 100 repos is 8 statements but still scores every repo** to
  find the C/D/E ones; fine at 100, and a materialised health column would be
  the eventual answer at thousands.
- **Snapshot-count noise in the fixture**: `before-3repos.json` shows 1,536
  snapshots and `after-3repos.json` the same after `down`; the fixture is
  clean.
