## How to use this list

- Each item is a checkbox with an id (`INS-07`), a severity, the problem, a suggested fix, and the screen and file it concerns.
- Severity: **P0** the user cannot finish the flow · **P1** a missing step, a real risk or major confusion · **P2** friction · **P3** polish.
- Items that start with "Missing step:" are steps the flow needs and the product does not have yet.
- Items added after the first pass carry the pass that found them, for example _(pass 2)_.
- When an item becomes a ticket, add the ticket id after it, e.g. `→ W20-03`. Tick it when the fix is merged.

### P0 items (fix first)

- [x] `FND-01` **P0** → W20-01 The finding detail only offers Confirm and Dismiss. Neither is disabled for the current status, so on a dismissed, resolved or won't-fix finding both buttons return a 409, and confirmed→resolved ("fixed"), open→won't fix and any reopen cannot be done from the UI at all → show only the actions the lifecycle allows for `finding.status`: Mark fixed (resolved), Accept risk / Won't fix, Reopen, and Dismiss with a reason. _(Finding detail; `apps/web/src/widgets/findings/FindingDetail.tsx:240`, `packages/insights/src/findings/lifecycle.ts:20`)_
- [x] `FND-69` **P0** → W20-01 In Settings → Rules, the Promote, Accept-to-shadow and Deprecate buttons can never work. The mutation is declared as `{ endpoint: '/rules/{ruleId}/transition', method: 'POST' }` with no `path`, and the rule id is sent only in the body. `buildUrl` only replaces placeholders listed in `path`, so the request goes to the literal URL `/api/v1/rules/{ruleId}/transition`. The API looks up a rule named "{ruleId}" and returns 404 "Rule not found" for every press. Because the page never shows `transition.error`, nothing appears on screen at all. Once any rule is in the registry, its lifecycle cannot be moved from the UI → declare the mutation per row with `path: { ruleId: rule.rule_id }` (or build the URL inside the mutation function), send only `{ to }` in the body, and add a test that checks the URL the request hits. _(Settings → Rules; `apps/web/src/routes/admin/rules.tsx:27-30`, `apps/web/src/routes/admin/rules.tsx:101-106`, `apps/web/src/api/client.ts:76-77`, `apps/api/src/routes/rules/index.ts:152-168`)_ _(pass 5)_
- [x] `DSH-01` **P0** → W20-01 Clicking Share shows a link `/views/shared/{slug}`, but the web app has no route for that path, so whoever receives the link gets "Page not found". The share flow cannot be completed. → Add a `routes/views/shared/$slug.tsx` that reads `GET /views/shared/:slug`, show the full absolute URL, and add a Copy button. _(Saved view detail; `apps/web/src/routes/views/$viewId.tsx:79`)_
- [x] `ADM-01` **P0** → W20-01 Missing step: there is no way to add a member from the UI. `CreateUser` is built and tested but not mounted anywhere (its own comment says "not rendered anywhere yet"), so a self-hosted admin can only create accounts with curl → render `<CreateUser/>` above `<Members/>` in the members route and link it from the Members empty state. _(Settings → Members; `apps/web/src/widgets/auth/CreateUser.tsx:13`, `apps/web/src/routes/admin/members.tsx:5`)_
- [x] `ADM-02` **P0** → W20-01 Missing step: you cannot sign out of the app. The user menu only holds the persona picker. The only sign-out buttons in the code are on the stuck-session screen and the forced password change screen → add "Sign out" and "Change password" to the UserMenu and to the phone NavDrawer. _(Shell user menu; `apps/web/src/components/shell/UserMenu.tsx:41-73`)_
- [ ] `ADM-42` **P0** → W20-02 Report PDFs and the in-app report viewer cannot work in a packaged install. The worker image is plain `node:alpine` with no Chromium (Playwright's browser is never installed, and Alpine/musl is not supported by it), so every Generate ends "failed" with a raw Playwright launch error and Retry fails the same way. Even a successful print would be written to the worker container's own `./.data`: the api and worker share no report-data volume and compose never sets `DATA_DIR`, so the api's `stat`/`readFile` on the `file://` URI always misses. Every ready row would then read "PDF no longer on disk" and the viewer would read "This report has no stored data". The worker also prints by loading `PUBLIC_BASE_URL`, which it may not be able to reach from inside the compose network → install a browser in a Debian-based worker image (or print through a sidecar), mount one named `reportdata` volume at the same `DATA_DIR` in api and worker, point the printer at the internal `web` service, and add a packaged-install smoke test that generates and downloads one report. _(Reports → Generate / PDF / View; `Dockerfile:123`, `deploy/compose.yaml:88-97,120-153`, `apps/api/src/workers/index.ts:878`)_ _(pass 2)_

## 1. Install, first run and onboarding

<details><summary>Flow as a user walks it</summary>

1. Read README.md, then docs/INSTALL.md. Get a bundle and run `install.sh` (or `configure.sh` + `up.sh` from a checkout), with `--url`, `--admin-email` and the password in `ADMIN_PASSWORD`.
2. `up.sh` prints "All services running. Open http://localhost:8099", and you check `/healthz`.
3. First visit: "Checking your session…" (SessionProbe), then SignedOut decides between the sign-in screen and the password change.
4. Sign in as the bootstrap admin with the local form (OIDC or GitHub buttons only if configured).
5. Forced "Choose a new password" screen.
6. The app shell loads on Overview. The persona dialog opens over the "Welcome to RepoPulse" empty state, and the ForgeLinkBanner and DemoBanner sit above it.
7. Press "Not now", then the welcome CTA "Connect an organization", which goes to /admin. That page is titled "Settings", with System health first and then the "Connect an organisation" form.
8. Pick a forge, enter the instance URL and paste a token, then press Connect (alternative: `pnpm connect:forge` CLI from a checkout).
9. RepoPicker "Select repositories to track": tick repos, press "Track N repo(s)", backfill is queued.
10. Settings → Sync (SyncOps + dead-letter queue) to watch the backfill. SSE toasts and the Overview sync banner run meanwhile.
11. /setup checklist (the last tab in Settings) to see what is still outstanding.
12. Overview, Repositories and repo tabs fill in. Onboarding checklist appears on Overview.
13. First scan: Repo → Security → "Run scans now"; the CVE scanner needs `deploy/scan-db-sync.sh` first.
14. Demo variants: `deploy/demo.sh` (fixture forge, empty) and `DEMO_MODE=1 pnpm dev` (seeded).

## 2. Scans, findings and triage

<details><summary>Flow as a user walks it</summary>

1. Open Repo → Security. The Coverage table lists every scanner with its state, last run and open count, plus a note on the vulnerability database and the tools not in this build.
2. Press "Run scans now" (admin only). The button changes to Starting… → Queued… → Scan running…, the table refreshes every 4 seconds, and a "settled" line appears when the scan ends. If no worker picks the job up within 5 minutes, a "stalled" warning appears.
3. Scroll past the AI review pass panel and the Coverage map ("what was not looked at") to Open findings (the top findings, each linked to /findings?finding=), Secrets, Vulnerable dependencies (CVE table), the dependency funnel from raw to triaged (with VEX counts) and Attack chains.
4. Follow a finding or "All N open findings" to Reviews (/findings). Set filters (dimension, status, minimum severity, scanner, in a chain, rule, rule stage, verification), page with Previous/Next, select rows and bulk Confirm or Dismiss with a note.
5. Click a row to open the finding detail: an inline panel on desktop, a full-screen overlay below 1024px. It shows evidence code, a forge link, the recommendation, a verified fix, AI suggestions, rule precision and history. The note field is required, then Confirm, Dismiss (with a reason), Copy review summary or Close.
6. Or press "Triage queue (n)": a full-screen stepper driven by j/k/c/d/Esc over the current page.
7. Or use Repo → Findings: one unfiltered table of this repository's findings, using the same detail panel.
8. Side routes: Sensitive changes (radar list plus shadow signals), Settings → Rules (rule registry with promote/deprecate, rule precision and benchmark tables), Governance (AI-code comparison).
9. CI: an admin mints a read-only token with curl, and the pipeline pulls new PR findings through `repopulse.mjs check` (docs only, nothing in the UI).

## 3. AI layer: models, routing, AI passes, scheduled passes, verified fixes

<details><summary>Flow as a user walks it</summary>

1. 9. The engineer presses "Draft a verified fix", waits, then copies or downloads the patch. The admin looks over all attempts in Admin → Verified fixes.

## 4. Dashboards, repo pages and insights

<details><summary>Flow as a user walks it</summary>

1. The user signs in and lands on Overview (`/`). They see Next actions, Delivery KPIs, Repo health, Needs attention, Weekly pulse, Hotspots, then the plan, security, risk and AI-governance tiles.
2. They pick a repo from a health tile, from Needs attention or from Repositories (`/repos`). They land on Repo → Pulse, which has a header (name, risk-axis letters, health badge, "why?") and 10 tabs.
3. They move between tabs: Activity, Performance, Hotspots, PR Flow, AI Reviewers, CI, Findings, Security, Code Health.
4. They drill from a hotspot to the file page (`/repos/:id/files/*`). There they read churn, owners, findings, hotspot history and PRs, and they set an intent.
5. They drill from a file or PR to a finding. That lands on the repo Findings tab or the global `/findings`, depending on which link they used.
6. A developer goes to My Focus (`/me`) or Pull Requests (`/pull-requests`), then to PR detail.
7. A lead opens Improvement plans (`/plans`) to generate a plan, then accepts, starts or dismisses items.
8. A lead or exec opens Saved Views (`/views`), uses a template, edits the layout, clicks Share and Set as home, and sends the link to others.
