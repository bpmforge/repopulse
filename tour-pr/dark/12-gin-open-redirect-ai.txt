Client-controlled X-Forwarded-Prefix can yield a scheme-relative (open) redirect Location
○ low
confidence 3/5

Status: Open
The issue
GO
gin.go
L813
Wrap
Copy
p = prefix + "/" + req.URL.Path

gin.go:813–819

Opens the default branch — this finding records no commit, so the lines may have moved since it was raised.

What to do

After building p, collapse leading slashes (e.g. apply removeRepeatedChar(p, '/') or trim leading '/' before prefixing with a single '/'), and reject or ignore a prefix that is only "/" so the resulting Location can never start with "//".

Why this applies

When X-Forwarded-Prefix is "/", path.Clean returns "/", which passes the != "." check. sanitizePathChars and removeRepeatedChar then leave prefix as "/", and the concatenation p = prefix + "/" + req.URL.Path produces a path starting with "///" (e.g. "///foo"). removeRepeatedChar is applied to prefix only, not to p, so the leading slashes are not collapsed. redirectRequest then sends this as the Location. Browsers treat "//host"-style Locations as scheme-relative, so the redirect can point to an arbitrary host. The header comes from the client, so the impact is limited to the requester unless an upstream proxy passes an attacker-influenced header through, which would make it a cache or redirect-poisoning risk.
